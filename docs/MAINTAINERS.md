# Передача репозитория и выпуск

## Смена GitHub-владельца

Предпочтителен штатный Transfer ownership: он сохраняет историю, issues, звёзды и releases. Новый аккаунт должен подтвердить email и принять перенос; в нём не должно быть другого репозитория с тем же именем.

1. Убедитесь, что переносится только Community-репозиторий. Не подключайте приватный сервер или его данные.
2. Проверьте Settings → Webhooks, Deploy keys, Secrets and variables и Environments. GitHub сохраняет эти настройки при переносе: удалите ненужные интеграции, если добавляли их самостоятельно.
3. В Settings → General → Danger Zone → Transfer ownership укажите новый аккаунт. Новый владелец принимает перенос по письму GitHub.
4. Обновите `origin` локального checkout на новый `OWNER/REPOSITORY`.
5. Замените публичные ссылки старого владельца в `README.md`, `docs/index.html`, `docs/guide.html`, `docs/isolation.html`. Обновите команды клонирования.
6. Включите / проверьте Pages: branch `main`, folder `/docs`. Старый адрес GitHub Pages **не перенаправляется автоматически**. Новый адрес зависит от нового владельца и имени репозитория.
7. Проверьте доступность нового сайта, ссылок GitHub и скачивания release. Проверьте private vulnerability reporting, secret scanning и push protection, доступные новому аккаунту.
8. Просмотрите Collaborators: GitHub добавляет прежнего владельца как collaborator. Уберите доступ, если он больше не нужен.

GitHub перенаправляет старые адреса самого репозитория. Не создавайте новый репозиторий на прежнем месте: это может убрать перенаправление.

Официальная инструкция: <https://docs.github.com/en/repositories/creating-and-managing-repositories/transferring-a-repository>.

## Доступ без пересылки секретов

Достаточно авторизовать GitHub CLI через браузер под нужным аккаунтом. Пароль, одноразовые коды, personal access token и ключи не публикуются в issues и не отправляются в чат. Можно также оставить доступ прежнему аккаунту только к переданному репозиторию, используя Collaborators.

## Перед выпуском

```sh
npm ci
npm run check
npm test
npm run audit:public
npm audit --omit=dev
```

Затем:

- Проверьте новую установку на пустом хранилище, актуальном Node.js LTS и HTTPS-хабе.
- Проверьте один реальный запрос у каждого поддерживаемого провайдера на отдельной тестовой подписке; не представляйте mocked/API-тесты как проверку Claude/Codex.
- Проверьте обе архитектуры Mac, свою подпись/обновления и iPhone, если публикуете соответствующие сборки.
- Сохраните резервную копию собственного хаба перед обновлением. Community-репозиторий не должен содержать эту копию.
- Укажите известные ограничения и уровень готовности релиза.
- Собирайте общий source release через `git archive`, а не архивированием рабочей папки с `.env`, `node_modules` и данными.
- Настройте локальный pre-push / CI в своём аккаунте для этих команд. Автоматический CI в исходной публикации не включён; наличие команд в документации не означает, что GitHub запускает их сам.
