# Обновления Team Room Community

## Для пользователя

Обновления предлагаются из публичных релизов `iintuziasty-web/team-room`. Проверка и установка — разные действия. Приложение не устанавливает новые версии само.

### Сервер и веб-приложение

Владелец пространства открывает профиль → **Обновления Team Room**:

1. «Проверить обновления» показывает версию и описание.
2. «Подготовить обновление» скачивает пакет, проверяет подпись и SHA-256, распаковывает новую версию отдельно и устанавливает её зависимости без запуска npm lifecycle scripts.
3. «Установить и перезапустить сервер» запрашивает подтверждение. При активных задачах, передачах и других незавершённых действиях установка блокируется.
4. Управляющий процесс завершает сохранение, создаёт копию основной базы, запускает новую версию и ждёт подтверждения старта. При ошибке запуска возвращаются прежняя версия и сохранённая основная база.

Адрес сервера, переменные окружения, пользователи, ключи и рабочее хранилище не входят в релиз и не заменяются его содержимым. Программа обновляется на вашем сервере. Для хаба с несколькими участниками версия меняется у всех участников этого хаба после его обновления.

Отключить периодическую проверку можно в том же разделе. Явная проверка по кнопке остаётся доступна. Телефон и браузер получают веб-интерфейс после обновления своего хаба; отдельный App Store-релиз для Safari-версии не нужен.

### Однократный переход с 1.0.0

Старые версии не содержат этой кнопки. На своём сервере дождитесь завершения работы и остановите прежний запуск, затем:

```sh
git pull --ff-only
npm ci
npm start
```

Новый `npm start` запускает управляющий процесс `launch.mjs`. Прямой запуск `node server.mjs` остаётся возможным для разработки, но кнопка установки сервера в нём недоступна.

Для Docker один раз пересоберите свою установку:

```sh
docker compose up -d --build
```

Railway-пользователям нужно один раз развернуть образ с 1.1.0 и постоянным volume. Контейнеру не требуется доступ к Docker socket: последующие версии запускаются из отдельного каталога на собственном volume. Если Node.js в базовом образе станет слишком старым, интерфейс попросит сначала обновить образ.

### Mac

Скачайте общий ZIP Mac из [релизов](https://github.com/iintuziasty-web/team-room/releases), распакуйте и перенесите **Team Room Community.app** в «Программы». При первом запуске укажите адрес **своего HTTPS-хаба**. Адрес хранится в настройках приложения отдельно от обновляемого `.app`.

Следующие версии: меню Team Room Community → **Проверить обновления…** → «Загрузить обновление» → «Установить и перезапустить». Подпись релиза, SHA-256, bundle ID и версия проверяются до установки. Общая сборка с чужим встроенным адресом хаба отклоняется. Настройки адреса, cookies и установленные подключения остаются на вашем компьютере.

После успешного обновления временный пакет удаляется; сохраняется одна предыдущая Community-сборка. Неудачные старые подготовки очищаются при следующей попытке после суток. Другие приложения и их резервные копии не удаляются.

Проверка в фоне только меняет пункт меню при наличии новой версии. Её можно выключить через «Проверять обновления автоматически». Замена приложения требует явного нажатия. Фоновое подключение обновится из принятой вами новой сборки после завершения его задач.

Сборка без Developer ID / Apple notarization может потребовать разрешения Gatekeeper при первоначальной установке. Механизм подписи релизов Ed25519 не заменяет подпись Apple.

## Хранение и восстановление

Серверные версии находятся в `.community-updates/` внутри `TEAM_ROOM_DATA_DIR`. Исходный checkout/образ остаётся неизменным. Хранятся текущая и предыдущая подготовленные версии, а также резервная копия основной базы. Не публикуйте этот каталог: копия базы содержит ваши данные.

Для резервного копирования по-прежнему сохраняйте весь свой каталог данных, включая ключи и рабочие файлы. Копия основной базы при обновлении не заменяет полноценный backup. Откат при сбое запуска не обещает совместимость произвольных будущих миграций: канал принимает только поддерживаемую схему данных.

Повторный запуск после прерванной установки восстанавливает предыдущее состояние до приёма новой работы. Ручная установка более новой версии checkout/образа получает приоритет над старой версией из volume.

## Для автора релизов

1. Внесите изменения, увеличьте `version` в `package.json` и корневых полях `package-lock.json`.
2. Опишите новые возможности и ограничения в `RELEASE_NOTES.md`.
3. Выполните проверки, зафиксируйте чистый commit:
   ```sh
   npm ci
   npm run check
   npm test
   npm run audit:public
   npm audit --omit=dev
   ```
4. Если менялись Mac-оболочка или Connect, соберите общий Mac-релиз:
   ```sh
   npm run build:mac -- --no-dmg
   ```
   Не задавайте `TEAMROOM_HUB_URL` для общей сборки. При необходимости индивидуальной сборки этот параметр остаётся доступен; общий канал не принимает её как универсальное обновление.
5. Подготовьте подписанные файлы:
   ```sh
   npm run release:prepare -- --key /path/outside/repository/signing-key.pem --mac mac-app/dist/Team-Room-<version>-macOS-universal.zip
   ```
   Путь — обозначение вашего локального файла. Закрытый ключ храните отдельно от исходников, делайте защищённую резервную копию. В коде находится только публичный ключ проверки. Потеря ключа потребует нового ручного bootstrap доверия.
6. Проверьте подготовленный пакет на отдельном временном хабе:
   
       npm run release:verify -- --release dist/releases/v<version>
   
   Проверка использует синтетическую предыдущую версию, свежую установку зависимостей и вымышленного пользователя. Запросы к моделям не запускаются.
7. Создайте GitHub release `v<version>` из проверенного commit и загрузите файлы из `dist/releases/v<version>/`: `team-room-update.json`, архив исходников и ZIP Mac. Опубликуйте как обычный Latest release. Draft/prerelease не предлагаются stable-каналом.

Сам push в GitHub не является выпуском обновления. Нужен подписанный опубликованный релиз; иначе пользователям нечего устанавливать. Частный ключ не хранится в GitHub Secrets в этой конфигурации; без него простой доступ на запись в GitHub недостаточен для создания доверенного обновления.

Проверки получают только общедоступные файлы GitHub. Токены хаба, проекты, переписки и адрес личного хаба на канал не отправляются. Как при любом сетевом запросе, GitHub видит IP и стандартные сетевые метаданные.

### Собственный канал для своей сборки

При сборке с `TEAMROOM_UPDATE_PUBLIC_KEY` Mac использует прежний механизм индивидуальных релизов со своего хаба. Для полного отключения обновлений сборки задайте `TEAMROOM_UPDATE_CHANNEL=off`. Ключи сторонних каналов не подмешиваются в общий stable-канал.
